Connecting systems that were never designed to connect

The practical lessons I keep relearning while building integrations, APIs, and data pipelines between independent systems.

September 1, 2026 5 min read Updated September 1, 2026

Connecting two systems is rarely a matter of sending data from point A to point B. The difficult part is agreeing on what the data means, what happens when one side is unavailable, and how a person can understand the result later.

Start with contracts

An integration becomes easier to reason about when its contract is explicit. Define the shape of every request and response, the required fields, the allowed states, and which system owns each piece of information.

This contract is more than documentation. It is a boundary that lets each system evolve without silently changing the meaning of the other system's data.

Design for failure

Networks fail, credentials expire, rate limits appear, and third-party responses change. A reliable pipeline treats these events as normal states rather than exceptional surprises.

Retries should be deliberate and bounded. Operations should be idempotent where possible, so repeating a request does not create duplicate work. When a message cannot be processed, it should become visible in a retry queue or dead-letter flow instead of disappearing into a log file.

Make the invisible visible

When someone asks why a record is missing, the answer should not require guessing. Give each operation a correlation ID and carry it through requests, jobs, database writes, and error reports.

Useful observability is not a wall of logs. It is a small set of signals that answers three questions quickly: what happened, where did it stop, and can it be safely run again?

The useful boundary

The best integration boundary is one that makes both systems simpler. It keeps ownership clear, gives failures a place to go, and leaves enough evidence for the next person to understand the journey of a piece of data.

That is the part I now look for first: not just whether two APIs can communicate, but whether the boundary between them can be trusted.
